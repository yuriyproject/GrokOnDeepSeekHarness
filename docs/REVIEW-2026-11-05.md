## Always-allow semantics

DSH 0.2.2-rc.1 has no persistent per-action grant the bridge can use. An approval answer is only `allowed-once`, `rejected`, `cancelled`, or `unavailable`. `allowed-once` is the only grant, and it covers that one requested action. The ask carries the tool name, an optional call id, and a reason. It cannot say "allow this kind of action for the rest of the session."

Session policy is only `ask` or `never`. `never` means never approve: the service rejects the ask before any answerer. Full access is the `danger-full-access` preset, which sets that sandbox mode and approval `never`, so prompts are skipped for the whole session. That is a session mode, not a grant stored on one action. The shared approval card can show an optional Always allow button, but the tool panel does not pass it, and no packaged caller wires `onAlways`. Tool approvals stay one-shot.

`allow_always` and `reject_always` are intentionally never sent for a DSH decision. A bridge-invented grant would bypass the DSH approval audit (`approval/asked` and `approval/decided` on every ask).

Sources: `@deepseek-ai/dsh-user-approval/lib/types/index.js` and `README.md` ("Only one-shot grants exist"); `@deepseek-ai/dsh-client-ui-approval/lib/client.js` and `README.md`; `@deepseek-ai/dsh-permission-presets/lib/types/index.js`; `@deepseek-ai/dsh-sandbox-policy/README.md`; `@deepseek-ai/dsh-tools/lib/pipeline.js`.

### MCP forwarding

(a) There is no settings document of MCP servers. Each server is one Loader row of `@deepseek-ai/dsh-mcp-client` (`dsh-mcp-client/lib/index.js` Config: `transport` `stdio` or `streamable-http`, `serverName`, plus `command`/`args`/`env`/`cwd` or `url`/`headers`). A plugin reads active rows from `ctx.loader.entries()` (`entry.fiber.effectiveConfig` while `state === 2`). `Config.listConfigs` (`dsh-tool-cordis` `queryLiveConfig`) returns schema only. Agent-preset plugins sit on a `PresetTree` that detaches from the host loader (`dsh-agent-preset-registry/lib/index.js`), so that walk misses them. `dsh-settings` is a generic editor. Bundles add rows through `templates/mcp/cordis.patch.yml`.

(b) Yes. The client README puts tokens in `env` and `headers` with Loader `!!js`. Resolved `effectiveConfig` holds the plain strings. Stdio spawn scrubs ambient `KEY`/`TOKEN`/`SECRET`/`PASSWORD` and `DSH_*`, then merges the configured `env` back on top.

(c) ACP `McpServer` (`@agentclientprotocol/sdk/schema/schema.json`): stdio has no `type` and is required of every agent (`name`, `command`, `args`, `env`); `http` and `sse` (`name`, `url`, `headers`) only when `mcpCapabilities.http` / `.sse` are true; unstable `acp` uses `serverId`. `docs/VERIFICATION.md` records the Grok 1.0.70 handshake and does not print `mcpCapabilities`. The stated advertisement is `http: true`, `sse: true`. Stdio needs no flag. DSH's ACP server (`dsh-acp/lib/index.js`) advertises only `{ http: true }`, mounts stdio and `http` as `streamable-http`, and rejects other types. It requires an absolute `command`.

(d) Yes. The ACP payload can carry the resolved env and headers, and logs use `redactMcpServers` (`***` for those values; URL userinfo and query stripped). Error text is scrubbed the same way. `forwardMcp` defaults to false, so `session/new`, resume and load still send `[]` until it is set. Preset-scoped servers and stdio `cwd` (not an ACP stdio field) are not forwarded.

Decision: implemented the opt-in. The host loader is a clear source, and secrets stay out of logs. Default remains off.

## Grok id inside the session log

A new event type written with `Session.append` is not safe. That method never sets `ignorable`. `validateStoredEvents` in `@deepseek-ai/dsh-session-persistence/lib/index.js` refuses any type outside `KNOWN_SESSION_EVENT_TYPES` (`@deepseek-ai/dsh-session/lib/index.js`) unless `ignorable` is exactly true, and that refusal rejects the whole stored log. `restoreReleasedV4Artifact` in `@deepseek-ai/dsh-session-format-v3-to-v4/lib/index.js` does the same for a current v4 artifact.

`appendPluginRecord` in `@deepseek-ai/dsh-session/lib/index.js` is safe on DSH 0.2.2-rc.1. It writes `plugin:<segments>` with `ignorable: true`. A reader that does not know the type keeps the event and skips it: `validateStoredEvents`, `adoptSessionEvent`, and `surfaceOpOf` all allow that marker. Removing this plugin does not make the session unreadable. `PluginRecordMap` is a TypeScript catalog, not a runtime allow-list. `pluginRecordOf` only recognises the `plugin:` grammar. Resume and fork keep the record.

A later format migration keeps plugin records only on a best-effort basis, so the link can disappear on a future upgrade, but that drop does not reject the log. DSH's plugin guide says callers outside `packages/experimental` must not call `appendPluginRecord`. There is no runtime gate. This bridge uses it because the same 0.2.2-rc.1 install still opens the session after the plugin is removed. The JSON map stays the primary link.
